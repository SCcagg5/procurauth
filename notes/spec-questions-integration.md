# Questions about the protocol text, from the reference edge

This file lists the places where the text of the protocol or of the MCP binding has two possible meanings. The edge chose one of them. Each item gives the paragraph, the question, and the meaning that the edge takes. The owner decides if the text needs a change. The files `spec-questions.md`, `spec-questions-cases.md` and `spec-questions-pep.md` list other questions.

1. **9.8, 1.4.** What is "the text of a key" in a request? The edge reads the header `Authorization` with the scheme `Bearer` and a text that is not empty. A request with another scheme, or with `Bearer` and no text, has no key. It gets `WWW-Authenticate: Bearer` with no error parameter.
2. **9.8.** What does the edge do with a request that has more than one header `Authorization`? The text does not say. The edge refuses it with `error="invalid_token"`. It does not choose one of the values.
3. **8.3, 9.8.** Which answer does a request get when the PDP gives no valid answer for `access`? Paragraph 9.8 covers a refused key only. The edge cannot decide, so it gives HTTP 503 with an empty body. It does not give a token.
4. **8.3, 9.8.** What does the edge do with a `false` answer that has the reason `budget_exceeded`? The edge asks for `access` with no `context.usage`, so no budget applies. The edge treats each `false` answer as a refused key: HTTP 401 with `invalid_token`.
5. **MCP 6.2.** Can an edge answer 400 to an MCP request when the HTTP request is not valid? The edge cannot read a key from such a request. It answers 400, 414, 431, 501 or 505 for a request that is not valid HTTP/1.1. It answers 413 for a body that is above its bound, but only after the key is good. It never answers 400, 404 or 405 for a request that it can read.
6. **9.8.** May the edge close the connection after a refusal? The edge needs no part of the body. It does not read it, so it closes the connection after the answer. It reads and drops the rest of the request for 2 seconds at most, so that the client reads the answer.
7. **9.9.** Can the edge give a kept token until `exp`? The text says "only before its `exp`". A service accepts a token until `exp` plus its skew, but a request that waits can reach the service after that time. The edge gives a kept token only until a quarter of its life remains.
8. **9.1.** Where does the text of a key occur in a request? Paragraph 1.4 names the header `Authorization`. The edge removes this header. It does not look for the text in another header, in the query or in the body.
9. **9.1.** What is "a header with the name of the token header"? The name has no case in HTTP. The edge removes each header with this name, in any case, and it sets one header with its own token.
10. **3.1, 9.3.** How does an edge authenticate a person? The protocol gives no way. The keys file of the reference edge can hold an entry for a person: an id with no colon and no owner. The token of such an entry has no `owner`. This is a test aid and not a rule of the protocol.
11. **9.4.** When must the edge put `kid` in the header? The text says: when the key set of the service holds more than one key. The edge does not know the key set of the service. The key `signing.kid` of the configuration tells it. The operator sets the key to the `kid` of the public key in the key set.
12. **9.2.** Is the maximum age a value of the edge? The text says that the operator sets the life of the token to no more than the maximum age of each service. The edge has the keys `token_life_seconds` and `max_token_age_seconds`. A life above the maximum age stops the program.
