# Questions about the protocol text, from the conformance cases

This file lists the places where the text of the protocol or of the MCP binding has two possible meanings. A conformance case had to choose one of them. Each item gives the paragraph, the question, the case that is concerned, and the meaning that the case takes. The cases take the most literal meaning. The owner decides if the text needs a change. The file `notes/spec-questions.md` lists the questions of the code.

1. **4.1, 11.1.** Which reason does a PDP give for a node id that is empty, has more than 256 bytes or has a control character? Paragraph 11.1 lists no reason for it, and 11.2 says that any other false answer has no reason. The case D23 checks the decision false and does not check the reason.
2. **10.3, 11.1.** Is an answer with `budget_exceeded` and a `retry_after` that is 0, or a text, not valid? Paragraph 11.1 says that `retry_after` is a whole number of 1 or more. The case U67 expects HTTP 503. No case tests an answer with `budget_exceeded` and no `retry_after`.
3. **8.3, 9.8.** Which status does an edge give to a key with a valid text whose subject has no true decision for `access`? Paragraph 9.8 gives HTTP 401 with `invalid_token` to an edge that refuses a key. The case E10 takes this meaning.
4. **4.3, 5.2.** Does a grant on a node above cover a node whose type is not in `resource_types` of the asked action? Paragraph 4.3 says that a grant covers each node below it. Paragraph 5.2 says that `resource_types` gives the types on which a grant is valid. No case tests this point.
5. **6.11.** What is the form of the answer to an Access Evaluations request that has no items? Paragraph 6.11 says that such a request can carry `context.usage`. The case D62 checks the status and the count of the unit. It does not check the form of the body.
6. **7.3, 7.5, 10.3.** A `context.limits` holds a budget value, or a ceiling value that is not a whole number. Is the answer not valid, and the PEP gives HTTP 503? Or is it a ceiling that the PEP cannot apply, and the PEP gives HTTP 403? No case tests this point.
7. **5.5a, 10.1a.** Must the PEP ask the other permission before the action of the use? Paragraph 10.1a shows this order, and it says that a false first answer sends no question with `context.usage`. The case U35 takes the order of the example.
8. **5.7.** Is a `parent` with a bad percent-escape, for example `%zz`, a bad parameter? Paragraph 5.7 says that a parameter is bad when its value breaks the rules of 5.7. The case U80 expects HTTP 400.
9. **10.7.** How many connections make a small fixed number? The case U69 expects one connection or two after four uses, one after the other. Its level is SHOULD.
10. **9.3, 9.4, 9.5.** Must a service accept a token for a key that has no `owner`? Paragraph 9.3 says that a token for a key also has `owner`. Paragraph 9.4 lists the claims that make a token bad, and it does not name `owner`. The case U10 expects that the service accepts the token.
11. **10.6.** After an HTTP error status of the PDP, can the PEP send a question with `context.usage` again? Paragraph 10.6 names a timeout, a lost answer and a connection error only. The case U68 tests the lost answer.
12. **9.2, 9.4.** Must each service trust a key with the algorithm `ES256` and a key with the algorithm `Ed25519`? The text names both algorithms, and the key set of the edge decides which key the service trusts. The case U52 sends a token with `ES256`.
13. **5.3c, 5.8, 7.1.** The cases U17 and U73 use the warnings of the core reader to check that a document stays within the numbers. The reader also gives a warning for an unknown member, and for a ceiling name that is not `max_` and a noun. Must a case check the numbers only?
14. **Binding 1.3, 5.3.** The tool error of 5.3 has `resultType` for the revision 2026-07-28. The cases that use an MCP operation use this revision. No case tests the form of the result for a legacy revision.
