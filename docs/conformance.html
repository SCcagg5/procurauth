Conformance

191 conformance cases as data, and the JSON schemas of the documents. Each case cites a paragraph of the protocol. A team that builds agents uses them to test that a service refuses a key beyond the rights of its owner, and that a spent budget stops the agent.

How the cases are organised

The cases are data, in the directory conformance/ of the repository. The repository has 191 cases: 99 in the series U, 74 in the series D and 18 in the series E. Each case cites the paragraphs of the protocol that it tests.

The series show who the case tests. A PEP, a PDP and an edge have their own series. For agents, the paragraphs that count most are 3.5 (a key never has more than its owner), 6.5 (the counting of a budget) and 10.3 (the refusals).

D74A PDP: decisions, coverage, limits, counters and reasons.Sections 3 and 4, 5.1 to 5.5, sections 6 to 8, 10.7, 10.7a, 11 and 12.

The MCP binding gives the ids U18, U23, U25 to U31 and E01 to the cases of its section 9. These cases are in the same directory, with exactly these ids. Each one cites a paragraph of the binding and has the condition no_mcp_endpoint.

Test directories

A PDP case names a directory file: the data that the PDP under test must hold. Each file is valid against the schema fake-pdp-data.

One case

A case has a list of steps. A step sends one request and checks the result. The schema is closed: an unknown member is an error. A case tests one rule and has one reason to fail.

MemberMeaning
idThe id of the case. The letter of the id is the series. The number has two or three digits.
titleOne sentence that states the rule that the case tests.
rolepep, pdp or edge.
paragraphsThe paragraphs that the case tests, for example ["7.3", "8.1"]. A paragraph of the MCP binding has the prefix mcp:.
requirementMUST or SHOULD. The failure of a SHOULD case is a warning.
skip_ifOptional. Conditions that make the runner skip the case, for example no_budget_action or no_mcp_endpoint.
givenThe set-up: directory, clock, counters, tokens and, for a PEP, pdp_script.
stepsThe steps in order. A step has an optional name and skip_if, a request and an expect.
notesOptional. A remark for the reader.

This case, D05, tests how a PDP combines ceilings. It uses Alice and the service of section 13 of the protocol. The file is conformance/cases/D/D05.json.

What a step can expect
Member of expectMeaning
status, headers, body_text, jsonThe HTTP answer. json names members by JSON Pointer.
valid_asThe body is a good action_document or options_answer, checked with the readers of the core.
pdp_questionsFor a PEP: the questions that the test PDP received during the step, with a count.
pdp_connectionsFor a PEP: the connections that carried a request during the case.
upstreamFor an edge: the request that reached the service behind the edge, its headers and the claims of its token.

The case cites 7.3, 8.1 and 8.4. A matcher has exactly one member: equals, absent, present, regex, not_regex or one_of. Schema: conformance-case.

Coverage

COVERAGE.md lists each paragraph that a role must follow, and the cases that test it. It has 130 rows (71 for a PEP, 48 for a PDP, 11 for an edge). 23 rows have no case. A second table lists 64 rules that no case can test, each with its reason. Examples: a case cannot see the effect of a ceiling, the age of a copy of the directory, or the memory of the PEP.

The tests of the crate schema-check read this file. They check the ids, the paragraphs and the roles, and that COVERAGE.md agrees with the cases.

Run the cases

Use access-conformance. It needs a profile: one JSON file with a section for each role. The run needs only the section of its role. A path in the profile starts at the directory of the profile. A secret comes only from a file. The examples are in crates/access-conformance/examples/. The tool speaks plain HTTP.

Against a PEP (series U)

The runner acts as the client, as the edge and as the PDP. It signs the identity tokens with a private key. The service must trust the public key and must call the PDP address of the profile. The profile maps each abstract operation (use_plain, use_budget, mcp_call_plain and others) to a request of your service. An operation that the profile does not define makes the runner skip the steps that use it.

pep.json (the head of the example)
{  "pep": {    "service": "datastore",    "token": {      "header": "X-Identity-Token",      "iss": "https://edge.example",      "max_age_seconds": 300,      "skew_seconds": 30,      "keys": [        {          "alg": "Ed25519",          "kid": "edge-ed25519",          "file": "test-edge-ed25519.pem"        },        {          "alg": "ES256",          "kid": "edge-es256",          "file": "test-edge-es256.pem"        }      ]    },    "pdp": {      "listen": "127.0.0.1:8181",      "credential_file": "pdp-credential.txt"    },    "answer_cache": false,    "options_type": "host",    "mcp": { "path": "/mcp", "session_budget": false },    "operations": { ... }  },  "timeouts": { ... }}
PEP
access-conformance --role pep --profile pep.json \    --url http://127.0.0.1:8000

The file crates/reference-service/PROFILE.md gives the profile of the reference service. A run is only useful if it can fail. This run uses the reference service with a maximum token age of 7,200 seconds. The service then accepts a token with a long life, and the case U48 fails. The result is real output.

Example, a failing run
$ access-conformance --role pep \    --profile conformance-profile.json \    --url http://127.0.0.1:8080U48  fail  9.4  step "A token with a long life": status: expected 401, found 200 (and 1 more)99 cases: 97 passed, 1 failed, 1 skipped$ echo $?1

Against a PDP (series D)

The runner sends the questions of the series D and compares the answers. The PDP under test must hold the directory of each case. The runner proves it first, with control questions that count nothing. For a test of the runner itself, set pdp.spawn_fake_pdp and give no --url: the runner then starts fake-pdp in its process.

pdp-fake.json
{ "pdp": { "spawn_fake_pdp": true } }
PDP, fake-pdp in the process
access-conformance --role pdp --profile pdp-fake.json \    --series D

For an external PDP, the cases that use a budget need a clock and counters that the runner controls. The profile gives pdp.load (a request that loads the data of a case), pdp.reset_url and pdp.clock_admin_url. fake-pdp --admin offers these requests. When the profile gives none of them, the runner skips these cases and prints the reason.

pdp-external.json
{  "pdp": {    "credential_file": "pdp-credential.txt",    "directory_check": {      "mode": "control_questions",      "max_questions": 100    },    "load": {      "url": "http://127.0.0.1:8181/__load",      "method": "PUT"    },    "clock_admin_url": "http://127.0.0.1:8181/__fake/clock"  }}
PDP, a separate process
access-conformance --role pdp --profile pdp-external.json \    --url http://127.0.0.1:8181

Against an edge (series E)

The runner acts as the client, as the service behind the edge and as the PDP. It sends three key texts, each in a file: a key that the edge accepts, a key that the edge knows but whose subject has no access, and a key that the edge does not know. It checks the identity token that arrives with the public keys of edge.trust. It starts fake-pdp on edge.pdp.listen.

edge.json
{  "edge": {    "service": "datastore",    "token_header": "X-Identity-Token",    "trust": {      "iss": "https://edge.example",      "max_age_seconds": 300,      "skew_seconds": 30,      "jwks_file": "edge-jwks.json"    },    "keys": {      "valid": {        "text_file": "edge-valid-key.txt",        "subject": "key:ann-k1",        "owner": "ann"      },      "no_access": { "text_file": "edge-no-access-key.txt" },      "unknown": { "text_file": "edge-unknown-key.txt" }    },    "upstream": { "listen": "127.0.0.1:9000" },    "pdp": {      "listen": "127.0.0.1:8181",      "directory": "access.json",      "credential_file": "pdp-credential.txt"    },    "mcp_path": "/mcp",    "token_cache": false  }}
Edge
access-conformance --role edge --profile edge.json \    --url http://127.0.0.1:8090

Read the result

ResultMeaning
passEach step of the case passed.
failA check of a MUST case failed. The exit code is 1.
warnA check of a SHOULD case failed. The exit code does not change.
skipThe case does not apply to the target, for example a service with no options route. The line gives the reason.

The summary line is N cases: P passed, F failed, S skipped, with , W warned when a SHOULD case failed. The exit code is 0 when no case failed, 1 when a case failed, and 2 for a usage error, a bad profile or bad data, or a target that is not reachable. --print-config checks the profile and prints the value that applies for each key. --format json writes the report of the schema conformance-report.

Results of the reference programs

The script scripts/conformance.sh [pep|pdp|edge|all] builds the programs and runs the runner against the reference programs. It starts all the processes in one Docker container. The container has no network and the repository is read only. A time limit of 600 seconds stops the run. The exit code is 0 when no case failed. scripts/ci.sh runs it after the tests.

What the cases do not test

No series tests the system that makes keys (3.2, 3.8) or the caller of the options route (5.6 to 5.9). The cases cover a PEP, a PDP and an edge only.

64 rules of the protocol have no case, with a reason in COVERAGE.md. For example, a case cannot see the effect of a ceiling, the security of the link to the PDP, or the memory of a PEP.
