Conformance

JSON schemas for the documents of the protocol, and conformance cases as data. Each case cites a paragraph of the protocol. A team that builds agents uses them to test that a service refuses a key beyond the rights of its owner, and that a spent budget stops the agent.

How the cases are organised

The conformance cases are data, in the directory conformance/ of the repository. Each case cites the paragraph of the protocol that it tests. A case has an id: a letter for the series and a number.

The series show who the case tests. A PEP, a PDP and an edge have their own series. For agents, the paragraphs that count most are 3.5 (a key never has more than its owner), 6.5 (the counting of a budget) and 10.3 (the refusals).

SeriesTestsCases cite

DA PDP: decisions, coverage, limits, counters and reasons.Sections 3 and 4, 5.1 to 5.5, sections 6 to 8, 10.7, 10.7a, 11 and 12.
EAn edge: the key, the identity token and the refusals of a key.1.4, 8.3, 9.1 to 9.3, the second paragraph of 9.4, 9.8 and 9.9.

The MCP binding holds the cases that only MCP needs: U18, U23, U25 to U28 and E01 (section 9 of the binding). The directory conformance/ gives none of these ids to another case, so its series E starts at E02.

JSON schemas

The directory schemas/ holds JSON schemas for the documents and the messages of the protocol. Use any JSON Schema validator. access-lint checks more than a schema can: the rules between members, for example that a limit name is declared.

SchemaChecksRules
action-document.schema.jsonThe action document of a service, with its types, actions and limit declarations.5.2, 6.1
options-answer.schema.jsonThe answer of the options route.5.8
identity-token.schema.jsonThe header and the claims of an identity token.9.2, 9.3
evaluation.schema.jsonThe members that the protocol adds to a question and to an answer: context.usage, context.limits, context.match and context.reason.6.4, 7.3, 11.1
case.schema.jsonOne conformance case.This page.
Check an action document
$ access-lint actions.json

One case

A case names its role and the data that it needs, gives one request and tells the expected answer. This case tests how a PDP combines two ceilings. It uses Alice and the service of section 13 of the protocol.

Conformance case, shortened
{  "id": "D07",  "title": "A ceiling takes the lowest value among the grants of the asked action",  "cites": ["7.3", "8.1"],  "role": "pdp",  "directory": "alice.json",  "request": {    "subject": { "type": "user", "id": "alice" },    "action": { "name": "data.read" },    "resource": {      "type": "table",      "id": "orders",      "properties": {        "ancestors": [          { "type": "service", "id": "datastore" },          { "type": "host", "id": "prod" },          { "type": "database", "id": "test2" }        ]      }    },    "context": { "usage": { "units": 1 } }  },  "expect": {    "decision": true,    "context": {      "limits": { "max_rows": 100, "max_duration": 30 },      "usage": { "units": 1 }    }  }}

The case cites 7.3 and 8.1: a ceiling takes the lowest value among the grants of the asked action that cover the resource.

Run the cases

Use access-conformance. Give it the URL of the implementation and its role. The tool prints pass, fail or skip for each case. It exits with 0 when each case passes.

Against a PEP

The tool acts as the edge and as the PDP. It signs the identity tokens and it answers the questions of your service, with the parts of access-token and fake-pdp.

  1. Start your service. Set its configuration to the issuer, the public keys and the PDP that the tool gives.
  2. Run the series U against the URL of your service.
  3. Read each failed case. Its line gives the paragraph that the case tests.
PEP
access-conformance --role pep --url http://127.0.0.1:8000

Against a PDP

The tool sends the questions of the series D and compares each answer with the expected answer. Load the directory of the case data into your PDP before you start. fake-pdp reads the same data, so you can compare the two.

PDP
access-conformance --role pdp --url http://127.0.0.1:8181

Against an edge

The tool acts as the client, with key texts, and as the service behind the edge. It checks the request that reaches the service. It also checks that the refusals of the edge have no body and that no key text goes on.

Edge
access-conformance --role edge --url https://edge.example

Read the result

  • pass: the implementation does what the paragraph says.
  • fail: it does not. The exit code is 1.
  • skip: the case does not apply, for example a service with no options route does not run the cases of 5.6.
JSON result
access-conformance --role pep \    --url http://127.0.0.1:8000 \    --format json

What the cases do not test

No series tests the system that makes keys (3.2, 3.8) or the caller of the options route (5.6 to 5.9).
