Version 1.0 Command-line tools and a library

Tools

Five command-line tools and a reference PEP library in Rust. They help you build and test an implementation of the protocol, for agents and for their services.

  • access-lint
  • fake-pdp
  • access-token
  • keycheck
  • access-conformance
  • PEP library
  • Get them

Why a team that builds agents wants them

An agent acts with a key. A team that builds agents, or services for agents, must know two things. A service refuses a key that goes beyond the rights of its owner. A spent budget stops the agent.

  • fake-pdp gives your service a decision point with a user, the key of her agent and their limits. Its counters run in memory.
  • access-token makes the identity tokens, good and bad, that the service must check.
  • access-conformance runs the cases. Each case cites the paragraph that it tests.
  • access-lint checks the action document, where the service declares its actions and limits.

Common rules

Each tool is a static program with no runtime to install. Each tool reads its input from a file, or from the standard input where the table says so.

Option or codeMeaning
--helpShows the usage and exits with 0.
--versionShows the version and the licence of the binary, and exits with 0.
--format text|jsonChooses the form of the output. The default is text.
Exit code 0No finding. The check passes.
Exit code 1The tool found at least one problem in the input or in the implementation.
Exit code 2The command line is not valid, or the tool cannot read its input.

access-lint

Checks an action document before a service publishes it.

What it does

Role
Finds each member that breaks the rules of the action document and of the limits (5.2, 5.3, 6.1, 7.1). It also checks an answer of the options route.
Input
An action document, as a file or as a URL. Optionally, a file of grant values to check against the document, or an answer of the options route.
Output
One line for each error, with the JSON path of the member and the number of the rule.

0 no finding1 findings2 usage error

Rules: 5.2, 5.3, 5.8, 6.1, 7.1.

Usage

Command
access-lint [--format text|json]            [--grants FILE]            [--options FILE]            <document>
Example
$ access-lint actions.jsonactions.json: 2 errors  $.actions[1].limits[2]  rule 5.2  undeclared limit  $.limits[0].min         rule 6.1  budget with "min"$ echo $?1

fake-pdp

A test decision point for the tests of a PEP.

What it does

Role
Answers as the protocol says for decisions, limits and reasons (sections 3 to 8 and 11), from fixed data. It runs one instance and keeps its counters in memory.
Input
A file of subjects, owners, grants and limit values, and the action document of each service. Optionally, a fixed clock and failures to make: HTTP 503, a delay or no answer.
Output
The AuthZEN 1.0 endpoints and the metadata on a local port. A log of each question, with its answer and the counters after it.

0 stopped on request2 usage error or bad data file

Rules: 6.5, 6.9, 7.3, 8.1, 11.1.

Usage

Command
fake-pdp [--listen ADDRESS:PORT]         <data-file>
Example
$ fake-pdp --listen 127.0.0.1:8181 directory.jsonfake-pdp 1.0 on http://127.0.0.1:8181metadata /.well-known/authzen-configurationq1  key:9b1c…  data.read  host:prod/database:test2    true  limits {"max_rows":5000,"max_duration":30}    counters  key/minute 99  alice/second 9              alice/minute 299

access-token

Makes and checks identity tokens for tests.

What it does

Role
Makes the tokens of the protocol, and also bad tokens for the tests of the checks of the service (9.4).
Input
To make a token: a signing key, the algorithm and the claims. For a bad token, set an old exp, a future iat, another typ or another alg. To check a token: the token and the configuration of the service.
Output
The token on the standard output. A check gives the result of each check.

0 no finding1 findings2 usage error

Rules: 9.2, 9.3, 9.4.

Usage

Command
access-token make --key FILE    [--alg Ed25519|ES256] [--typ TYPE] <claims>access-token check --config FILE    [--format text|json] <token>
Example
$ access-token make --key edge.pem \    --alg Ed25519 claims.json > token.jwt$ access-token check --config service.json \    token.jwtsignature  okalg        ok   Ed25519typ        ok   JWTiss        okaud        ok   datastoreexp        ok   life 300 s, max 300 siat        ok$ echo $?0

keycheck

Checks the text of a key. No store, no network.

What it does

Role
Tells if a text has the format of a key. It never writes the text to a log. The protocol defines no format (3.8), so the format is an input.
Input
The text on the standard input, never as an argument. A format file: a prefix, a length, an alphabet and a checksum.
Output
Good or bad, with the cause: prefix, length, alphabet or checksum. For a good text, its SHA-256 digest in hexadecimal and a hint of at most 4 characters of the random part.

0 no finding1 findings2 usage error

Rules: 2, 3.2, 3.8.

Usage

Command
keycheck [--format text|json]         <format-file>
format.json
{  "prefix": "mcp_",  "length": 53,  "alphabet": "A-Za-z0-9",  "checksum": {    "algorithm": "crc32",    "encoding": "base62",    "characters": 6  }}
Example
$ keycheck format.json < key.txtbad: length (expected 53 characters, found 47)$ echo $?1

access-conformance

Runs the conformance cases against a PEP, a PDP or an edge.

What it does

Role
Runs the series U against a PEP, the series D against a PDP and the series E against an edge.
Input
The URL of the implementation, its role and the cases to run. For a PEP, the tool also acts as the edge and as the PDP, with the parts of access-token and fake-pdp.
Output
Pass, fail or skip for each case, with the number of the paragraph, as text and as JSON.

0 each case passes1 a case fails2 usage error

Rules: section 15, item 2.

Usage

Command
access-conformance --role pep|pdp|edge    --url URL [--format text|json]    [--cases ID,ID,...]
Example
$ access-conformance --role pep --url http://127.0.0.1:8000U01  pass  3.3   subject type user, id taken from subU02  pass  4.1   chain in resource.properties.ancestorsU03  pass  9.4   bad signature gets HTTP 401U04  fail  10.3  budget_exceeded must give HTTP 429, got 403U05  skip  5.6   the service has no options route5 cases: 3 passed, 1 failed, 1 skipped$ echo $?1

Reference PEP library (Rust)

The steps of a PEP, ready for a service.

What it does

The library gives a service the steps of paragraph 10.0: the check of the identity token, the questions to the PDP, the kept answers and the map of the refusals. It is a reference for the authors of other libraries.

This specification gives no detailed API for the library. The README of the crate and the docs/ directory of the repository describe it.

Rules: 9.4, 10.0, 10.1, 10.3, 10.6.

Get it

Cargo.toml
[dependencies.procurauth-pep]git = "https://github.com/SCcagg5/procurauth"tag = "v1.0"

Test a service that uses it with access-conformance.

How to get them

Binaries

Each release has archives for Linux, macOS and Windows, and a file of SHA-256 sums. Download one, check its sum and put the five programs on your path.

Binaries of version 1.0

Source

The Rust workspace is in the repository, with the library. Build all the programs with cargo build --release.
